## 概念讲解：DI 的几种注册写法全解（承接上一问）
- 项目 27 处注册**全部集中在** `App.xaml.cs`（397~607 行），只有 Singleton / Transient，无 Scoped。
- 归纳钥匙：任何 `AddX` 都是「服务类型 × 怎么造 × 活多久」的组合，最终都落到 `services.Add(new ServiceDescriptor(...))`。
  五种实现来源：`AddSingleton<IFoo,Foo>()`（类型）/ `AddSingleton<Foo>()`（自注册）/
  `AddSingleton(instance)`（现成实例）/ `AddSingleton<IFoo>(sp => ...)`（工厂）/ `AddSingleton(sp => new Foo())`（工厂+推断）。
- 易错点已讲清：
  - instance 在**注册那一刻**就创建，容器**不 Dispose** 它，也无法注入依赖；
  - `AddSingleton(configuration)` 因变量静态类型是 `IConfiguration`，注册的是 IConfiguration（不是 ConfigurationRoot）；
  - `ILogger<T>` 从未显式注册，靠 `AddLogging` 内部 `ILogger<>` 开放泛型现造；
  - 8 个 `PageViewModel` 同接口多实现：`IEnumerable<PageViewModel>` 取全，单个解析只拿最后一个；
  - 工厂 lambda 的 `sp` 只在工厂内现取，不缓存、不能解析自己；工厂是单例故只跑一次。
- 项目里工厂注册的三个真实动机：构造参数用配置算出来的数组/数值（VirtualMotionCard、IdleMonitor）、
  需要探测+降级分支（Leadshine/Hikvision）、跨工厂共享手 new 的 `SemaphoreSlim dllLock`。

## 概念讲解：DI 注册顺序 / 循环依赖（用户问「DI 容器注册对象时有顺序要求吗，相互需要怎么办」）
- 结论：**注册顺序无关，解析顺序有关**。AddSingleton 只往 ServiceCollection 写一条描述，
  真正 new 发生在 BuildServiceProvider 之后首次 GetRequiredService（懒），容器按构造函数参数做后序遍历。
- 唯一受注册顺序影响：同一接口多实现时，单个解析取最后一个注册，`IEnumerable<T>` 按注册顺序返回
  （项目里 8 个 `PageViewModel` 的顺序最终由 ShellViewModel 按 PageKey 再排序，所以不受注册顺序左右）。
- **受解析顺序影响的项目实例**：`IMotionCard` 工厂内会置 `HardwareStartupReport.MotionDegraded = true`，
  而 `IIoService` 工厂读该标记决定是否跟着降级 → 必须先解析 IMotionCard 再解析 IIoService。
  `DeviceMonitor(IMotionCard, IIoService, ...)` 靠构造参数顺序隐性保证；`App.InitializeHardware` 显式先取 IMotionCard 更稳。
- 循环依赖：内置容器有检测，抛 `InvalidOperationException: A circular dependency was detected`（不死循环）。
  解法优先「抽中介者/拆接口」（项目里 `IDeviceMonitor` 同时注入三个硬件、硬件彼此不引用就是范例）>
  「事件反转依赖方向」> 「注入 IServiceProvider / Func<T> 延迟解析」（最后手段）；内置容器不支持属性注入。
- 生命周期方向：单例捕获 transient 不报错但会把 transient 变永久（LoginDialog/LoginViewModel 只能由
  App 直接用 Transient 解析，不得被单例注入）；项目无 scoped，不涉及根容器解析 scoped 报错问题。

## 原生 DLL 现状核查（用户问「dll 放哪里，项目里放了吗」）
- **结论：项目里一个原生 DLL 都没有。** `src/AutoTaping.Hardware/libs/` 目录不存在；
  `bin/Debug/net8.0-windows/` 里 37 个 dll 全是 NuGet 托管程序集 + OpenCvSharp/`e_sqlite3` 原生
  （在 `runtimes/win-x64/native/` 下），无 `LTDMC.dll`、无 `MvCameraControl*`。
- `appsettings.json` 中 `Hardware:UseVirtual = true` → 当前跑 VirtualMotionCard / VirtualCamera，
  原生 DLL 根本不会被加载，所以缺 DLL 不影响编译和运行。
- 项目已内建的约定：`AutoTaping.Hardware.csproj` 用
  `Condition="Exists('libs\MvCameraControl.Net.dll')"` → 定义 `HAS_MVS` + `<Reference>`；
  `HikvisionCamera.cs` 用 `#if HAS_MVS` 分真实实现 / 占位实现（占位 Initialize 恒 false → 降级 Virtual + AL201）。
- **LTDMC.dll 与 MvCameraControl.Net.dll 性质不同**：前者是纯原生（P/Invoke，无托管元数据），
  不能 `<Reference>`，只能 `<None CopyToOutputDirectory="PreserveNewest">` 复制；
  后者是托管封装，走 `<Reference>`。
- `AutoTaping.App.csproj` 未设 `PlatformTarget`（AnyCPU，x64 机器上跑 64 位）→ 必须用 x64 版 LTDMC.dll。
- `LeadshineMotionCard.Initialize` 已捕获 `DllNotFoundException` / `BadImageFormatException` /
  `EntryPointNotFoundException` 三种异常并返回 false，这就是降级到 Virtual 的入口。
