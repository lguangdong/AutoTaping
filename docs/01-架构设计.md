### 依赖规则（强制，Code Review 检查项）

| 规则 | 说明 |
|---|---|
| ✅ Core 只能依赖 `Microsoft.Extensions.Logging.Abstractions` | Core 保持纯净，可单元测试 |
| ✅ Core 通过**接口**使用 Hardware / Vision / Data | 接口定义放在 Core 的 `Abstractions/` 下 |
| ❌ App 不得直接 new 硬件类 | 全部通过 DI 注入接口 |
| ❌ Hardware 不得引用 Core 的具体业务类型 | 只返回基础类型（double / bool / 结构体） |
| ❌ 任何层不得直接写 `MessageBox` | 通过 `IUserNotifier` 接口 |
| ❌ Vision 不得依赖 Hardware | 视觉只吃 `Mat` / `BitmapSource`，由调用方协调 |

## 3. 线程模型

**这是本项目最容易出错的地方，必须严格按此实现。**

| 线程 / 上下文 | 职责 | 关键约束 |
|---|---|---|
| **UI 线程** | 渲染、用户输入、ViewModel 属性更新 | 严禁阻塞；严禁直接调用运控卡 |
| **流程线程**（1 个） | 执行 `AutoFlowEngine` 的步骤序列 | 长驻后台线程，用 `CancellationToken` 停止 |
| **采集线程**（1 个） | 轮询轴位置、IO 状态、通讯状态，200ms 周期 | 用 `System.Threading.Timer`，不要 while+sleep |
| **相机取图** | 走 SDK 回调或专用线程 | 回调里只做拷贝，不做处理 |

### 交互规则

```
UI 线程 ──(命令)──► 流程线程
流程线程 ──(事件/回调)──► UI 线程（必须 Dispatcher.Invoke / SynchronizationContext）
采集线程 ──(每 200ms 更新快照)──► UI 线程读取快照
```

### 禁止

- ❌ 流程线程里直接更新 `ObservableCollection`（会抛异常）
- ❌ UI 线程里 `Wait()` 流程线程（会死锁）
- ❌ 相机回调里做图像算法（阻塞取图，掉帧）
- ❌ 多个线程同时调用运控卡（DLL 非线程安全，**必须加锁**）

### 推荐实现

```csharp
// 采集线程 → UI 的快照模式（避免高频属性变更）
public sealed class DeviceSnapshot
{
    public double[] AxisPositions { get; init; } = new double[4];
    public bool[] DiStates { get; init; } = new bool[8];
    public bool[] DoStates { get; init; } = new bool[8];
    public DateTime Timestamp { get; init; }
}

// 每 200ms 由采集线程整体替换，UI 只读
private volatile DeviceSnapshot _snapshot = new();
```

## 4. 关键设计决策

### 4.1 为什么状态机而不是一堆 bool

设备有 6 个状态、多个互锁条件。用 bool（`IsRunning`、`IsPaused`、`IsAlarming`…）会出现非法组合（运行中又报警又暂停），且无法追溯迁移路径。

**用显式状态枚举 + 迁移表**，非法迁移直接抛异常并记日志。详见 `05-核心状态机与流程.md`。

### 4.2 为什么流程用"步骤列表"而不是一个大方法

自动流程有 15+ 步，每步都可能超时/失败/需要跳过。写成一个大方法会导致：
- 无法单步调试
- 异常时不知道停在哪一步
- 无法复用到"单步模式"

**用 `FlowStep` 列表 + 执行器**，天然支持：单步执行、断点续跑、步骤级超时、步骤级日志。

### 4.3 为什么硬件必须有 Virtual 实现

- 开发阶段没有硬件时能跑通全部 UI
- 面试/演示时不需要搬设备
- 单元测试可以注入 Virtual 实现做端到端测试
- **这是本项目"可演示"的关键**

Virtual 实现要求：
- `VirtualMotionCard`：按设定速度模拟运动耗时，位置线性推进，支持限位/急停/到位
- `VirtualCamera`：从 `images/` 目录轮播图片，模拟不同偏移
- `VirtualIoService`：内存数组，支持手动置位（在 IO 页调试）

### 4.4 为什么用 SQLite 而不是内存

- 断电后产量/报警不能丢（客户会查）
- 单机、零部署、免安装 → 工控现场最省事

### 4.5 为什么参数要写 appsettings.json + 数据库两张表

| 配置 | 位置 | 理由 |
|---|---|---|
| 硬件配置（轴行程、IO 映射、相机参数） | `appsettings.json` | 装机时设定，几乎不改 |
| 工艺参数（配方） | SQLite `Recipe` 表 | 频繁切换，需要版本管理 |

## 5. 启动流程（App.xaml.cs）

```
1. 配置 Serilog（文件 + 控制台）
2. 加载 appsettings.json
3. 注册全局异常处理器（DispatcherUnhandledException / AppDomain.UnhandledException / TaskScheduler）
4. 初始化 SQLite（建表 + 种子数据）
5. 注册 DI（Core / Hardware / Vision / Data / ViewModels）
6. 启动自检（SelfCheckService）：
   - 运控卡初始化（失败 → 降级为 Virtual + 报警）
   - 相机枚举（失败 → 降级为 Virtual + 报警）
   - 磁盘空间检查（< 1GB 报警）
   - 数据库可写检查
7. 显示登录窗口
8. 显示 MainWindow，进入 [空闲] 状态
9. 启动采集线程
```

**自检失败原则**：**永不阻断启动**，一律降级 + 报警。宁可功能缺失，也不能让操作工打不开软件。

## 6. 全局异常处理

| 场景 | 处理 |
|---|---|
| 流程线程异常 | 捕获 → 状态机转 `[报警]` → 记日志 → 通知 UI |
| 采集线程异常 | 捕获 → 记日志 → 标记通讯异常 → **线程继续运行**（不能死） |
| 硬件调用异常 | 包装为 `HardwareException`，带设备名 + 操作 + 错误码 |
| UI 未捕获异常 | 弹窗提示 + 记日志 + **不退出**（除非连续 3 次） |
| 致命异常 | 记日志 → 尝试安全停机（Z 抬起、关真空）→ 提示用户手动重启 |

## 8. 本文件的约束（AI 必须遵守）

1. 依赖方向不得反向（Core 不引用 Hardware 具体类）
2. 所有硬件交互必须走接口，不得在 ViewModel 里直接 P/Invoke
3. 采集线程与流程线程必须独立，不得合并
4. 运控卡调用必须加锁（`SemaphoreSlim` 或 `lock`）
5. 不得引入 README 中禁止的库
